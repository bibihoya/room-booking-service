# Meeting Room Booking Service

Сервис для бронирования переговорок с автоматической генерацией временных слотов на основе гибких расписаний. Проект демонстрирует опыт проектирования high-load API, работы с JWT, ролевой моделью (admin/user), нагрузочного тестирования и graceful обработки внешних зависимостей.

## Особенности

- Ролевая модель — Admin управляет переговорками и расписаниями, User создаёт/отменяет брони
- Автоматическая генерация слотов — 30-минутные слоты формируются на основе расписания (дни недели, часы работы)
- High-load ready — эндпоинт списка слотов выдерживает 274 RPS с временем ответа <10 мс (95-й перцентиль ~33 мс)
- Тестовое покрытие >40% + E2E сценарии (создание комнаты → расписание → бронь; отмена брони)
- Интеграция с Conference Service — опциональное создание конференц-ссылки с fallback-логикой при сбоях
- Docker Compose — полная контейнеризация, make up / make seed
- Swagger-документация — доступна после запуска на /swagger/index.html

## Быстрый старт

```bash
# 1. Клонировать репозиторий
git clone https://github.com/yourusername/meeting-room-booking.git
cd meeting-room-booking

# 2. Запустить сервис (PostgreSQL + приложение)
make up

# 3. Наполнить БД тестовыми данными (комнаты, расписания, слоты)
make seed

# 4. Остановить сервис
make down
```

Сервис будет доступен на `http://localhost:8080`.

## API и примеры

### Получение JWT

```bash
# Роль admin — создание комнат и расписаний
curl -X POST http://localhost:8080/dummyLogin \
  -H "Content-Type: application/json" \
  -d '{"role": "admin"}'

# Роль user — бронирование
curl -X POST http://localhost:8080/dummyLogin \
  -H "Content-Type: application/json" \
  -d '{"role": "user"}'
```

> В проекте также реализованы эндпоинты `/register` и `/login` (email/пароль) как расширение тестового задания.

### Основные эндпоинты

| Метод | Эндпоинт | Доступ | Описание |
|-------|----------|--------|----------|
| POST | `/rooms/create` | admin | Создать переговорку |
| POST | `/rooms/{roomId}/schedule/create` | admin | Создать расписание (дни недели, часы) |
| GET | `/rooms/{roomId}/slots/list?date=YYYY-MM-DD` | admin, user | Доступные слоты |
| POST | `/bookings/create` | user | Создать бронь (+ опционально ссылку на конференцию) |
| GET | `/bookings/my` | user | Мои брони (только будущие) |
| POST | `/bookings/{bookingId}/cancel` | user | Отменить бронь (идемпотентно) |
| GET | `/bookings/list?page=1&pageSize=20` | admin | Все брони с пагинацией |

## Архитектурные решения

### 1. Генерация слотов

**Подход:** Гибридный — слоты генерируются при первом запросе на дату и сохраняются в БД.

**Почему:**
- При 50 комнатах × 7 дней × 48 слотов = 16 800 слотов/неделю — хранить все заранее избыточно
- Генерация по требованию даёт:
    - Стабильные UUID для бронирования (необходимо для ссылок)
    - Естественное кэширование (повторные запросы той же даты не пересчитывают слоты)
    - Простоту реализации без фоновых воркеров

### 2. Хранение времени в расписании

**Решение:** Время хранится как `VARCHAR(5)` в формате `HH:MM`.

**Обоснование:** формат фиксирован, валидация через регулярное выражение, отсутствие операций с типами TIME снижает сложность.

### 3. Интеграция с Conference Service (опциональные ссылки)

При создании брони можно передать `{"slotId": "...", "createConferenceLink": true}`.

**Поведение при сбоях:**

| Сценарий | Решение |
|----------|---------|
| Сервис конференций недоступен | Бронь создаётся, ссылка = null, ошибка логируется |
| Таймаут (>2 сек) | То же самое — бронь создаётся |
| Сервис вернул 500 | Повтор 1 раз, если неудача — бронь создаётся без ссылки |

**Почему:** пользователь не должен терять возможность забронировать слот из-за проблем внешнего сервиса. Ссылку можно сгенерировать повторно (например, отдельный эндпоинт в будущем).

### 4. JWT и тестовые пользователи

Фиксированные UUID для ролей admin/user в `/dummyLogin` — это требование задания для стабильного тестирования. Для реальных сценариев реализованы `/register` и `/login` с хешированием паролей.

## Тестирование и нагрузка

### Юнит-тесты

Покрытие бизнес-логики: **40.2%** (превышает порог задания)

```bash
make test-cover
# Откроется coverage.html в браузере
```

### Интеграционные / E2E тесты

Два сквозных сценария (в `tests/e2e/`):
1. Создание комнаты → расписание → бронь пользователем
2. Создание брони → отмена брони (идемпотентность)

### Нагрузочное тестирование (k6)

**Сценарий:** запрос доступных слотов (самый высоконагруженный эндпоинт)

```bash
# Предварительно наполнить БД
make seed

# Запуск теста (50 VUs, 30 сек)
k6 run tests/load/slot-test.js

# Полная ступенчатая нагрузка (до 100 VUs)
k6 run tests/load/load-test.js
```

**Результаты:**

| Метрика | Значение | Требование |
|---------|----------|-------------|
| Успешность запросов | 100% | > 99.9% |
| Среднее время ответа | 9.61 ms | < 200 ms |
| 95-й перцентиль | 33.17 ms | < 200 ms |
| RPS (макс) | 274 | > 100 |

**Вывод:** сервис выдерживает нагрузку почти в 3 раза выше требуемой с запасом по времени ответа.
